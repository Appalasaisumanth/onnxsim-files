# 1️⃣ Big picture — what this file implements

This system schedules **LLM inference/training tiles** across cores.

Hierarchy

```
Request (prompt / generation job)
   ↓
Model
   ↓
Layers (Attention / FFN / etc.)
   ↓
Tiles (matrix compute chunks)
   ↓
Cores
```

Schedulers decide

* Which request runs
* Which layer launches
* Which tile goes to which core
* When barriers occur

# 3️⃣ High-level intuition

| Scheduler      | Analogy                                    |
| -------------- | ------------------------------------------ |
| Simple         | Run one model layer at a time on all cores |
| Time-Multiplex | Time-share cores across requests           |
| Dedicated CPU  | Each request gets fixed cores              |
| Half Split     | Spatially split cores across requests      |

# 5️⃣ Queue structure differences

## Simple / TimeMultiplex / Dedicated

Shared structures

```
_request_queue
_executable_tile_queue[partition]
_core_executable_tile_queue[core]
```

Flow

```
Layer → Partition queue → Core queue → Execution
```

---

## HalfSplitScheduler

Adds

```
_executable_tile_queue_table[request_id]
```

Flow

```
Layer → Request queue → Core subset → Execution
```

So tiles stay request-local.

# 6️⃣ Code behavior comparison

---

# 🔹 1. Simple Scheduler (Base)

### Layer launch condition

From `refresh_status()`

```
if request exists
AND all tile queues empty
AND no active layers
→ launch next layer
```

So

➡️ Strict sequential layers
➡️ No overlap

---

### Tile issuing

```
issue_tile_per_core()
```

Tiles distributed across all cores round-robin.

---

### Execution model

```
Layer 0 → finish → Layer 1 → finish → …
```

No interleaving.

---

### Use case

* Single inference
* Deterministic latency
* No batching

---

# 🔹 2. TimeMultiplexScheduler

Extends base scheduler.

Key change

### Request round-robin

From code

```
_request_rr = (_request_rr + 1) % _request_queue.size()
```

So next layer comes from different request.

---

### Layer overlap

Condition

```
if tile queues empty → launch layer from next request
```

So layers from different requests interleave in time.

---

### Core usage

All cores shared.

But time-sliced across requests.

---

### Execution example

```
Req1 Layer0
Req2 Layer0
Req3 Layer0
Req1 Layer1
Req2 Layer1
```

---

### Benefit

* Better throughput
* Fair sharing

Cost

* Cache thrashing
* Weight reloads

---

# 🔹 3. DedicatedCPUScheduler

Extends TimeMultiplex but overrides `refresh_status()`.

Key idea

➡️ Each request mapped to CPU partition.

From config

```
_partition_map
_cpu_to_partition
```

Example

```
Req1 → Cores 0–7
Req2 → Cores 8–15
```

---

### Layer launch rule

For each core

```
If its queue empty → launch layer of its request
```

So requests run truly parallel.

---

### Tile issuing

```
issue_tile_per_core(allowed_cpu, offset, partition_id)
```

Tiles only go to that partition’s cores.

---

### Execution model

```
Req1 uses cores 0–7 continuously
Req2 uses cores 8–15 continuously
```

No time sharing.

---

### Benefits

* Weight locality
* KV cache locality
* No context switching

Cost

* Idle cores if request small

---

# 🔹 4. HalfSplitScheduler (Spatial Split)

Most different design.

---

### Core assignment

```
target_id = core_id % request_count
```

So cores split evenly.

Example

| Core | Request |
| ---- | ------- |
| 0    | Req0    |
| 1    | Req1    |
| 2    | Req0    |
| 3    | Req1    |

---

### Tile queues

Per request

```
_executable_tile_queue_table[request_id]
```

No global queue.

---

### Layer launch

Each request launches layers independently when its queue empty.

---

### Tile execution

Core always pulls from its assigned request.

No stealing.

---

### Execution model

True spatial parallelism

```
Req1 Layer0 on cores 0,2,4
Req2 Layer0 on cores 1,3,5
```

---

### Benefits

* Strong isolation
* Predictable latency
* Parallel decoding

Cost

* Load imbalance
* Idle cores possible

---

# 7️⃣ Barrier handling differences

All schedulers respect

```
TileStatusBAR
```

Meaning

➡️ Next tiles wait until prior tiles finish.

But enforcement differs

| Scheduler     | Barrier strictness |
| ------------- | ------------------ |
| Simple        | Very strict        |
| TimeMultiplex | Medium             |
| Dedicated     | Medium             |
| HalfSplit     | Per-request only   |

---

# 8️⃣ Active layer tracking

All use

```
_active_layers_map
LayerStat
```

Tracks

* start_cycle
* finish_cycle
* launched_tiles
* finished_tiles
* remain_tiles

But

| Scheduler     | Scope             |
| ------------- | ----------------- |
| Simple        | Single request    |
| TimeMultiplex | Multi request     |
| Dedicated     | Per partition     |
| HalfSplit     | Per request queue |

# 11️⃣ When each is used (LLM inference)

| Scenario             | Best scheduler |
| -------------------- | -------------- |
| Single long prompt   | Simple         |
| Multi-user batching  | TimeMultiplex  |
| Multi-tenant serving | Dedicated      |
| Real-time decoding   | HalfSplit      |

# 12️⃣ Where IterLevelScheduler fits

Your first snippet

```
IterLevelSchedulercycle()
```

This is **request admission control**, not tile scheduling.

It

1️⃣ Moves requests → active set
2️⃣ Initializes prompt/gen phase
3️⃣ Calls model execution

So hierarchy

```
IterLevelScheduler → manages requests
Scheduler → manages tiles
```
