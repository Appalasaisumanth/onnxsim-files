## 1️⃣ What `SimpleInterconnect` represents

This is a **very simple cycle-accurate NoC / interconnect model**.

Key properties:

* **Fully connected**: every source can send to every destination
* **Per-(src,dest) FIFO** buffers
* **Fixed latency** (`_latency`)
* **Round-robin arbitration** per destination
* **One transfer per destination per cycle (max)**

No routing, no contention modeling beyond RR arbitration.

---

## 2️⃣ Internal state (the “attributes” you asked about)

These are the **important attributes** whose values define behavior:

```cpp
int _cycles;                      // global interconnect cycle
int _latency;                     // fixed transfer latency
int _n_nodes;                     // total endpoints

vector<vector<queue<Entity>>> _in_buffers;
// _in_buffers[src][dest] = FIFO of packets from src → dest

vector<queue<MemoryAccess*>> _out_buffers;
// _out_buffers[dest] = ready packets for dest

vector<bool> _busy_node;          // (currently unused)
vector<int> _rr_next_src;          // RR pointer per destination
```

Each `Entity`:

```cpp
struct Entity {
  uint64_t finish_cycle;   // when packet becomes deliverable
  uint32_t dest;
  MemoryAccess* access;
};
```

---

## 3️⃣ Constructor: `SimpleInterconnect::SimpleInterconnect`

### What happens BEFORE

Nothing exists yet.

### What happens INSIDE

```cpp
_latency = config.icnt_latency;
_cycles = 0;
_n_nodes = num_cores * ports_per_core + dram_channels;
```

Then:

* Allocate `_in_buffers[src][dest]` for all pairs
* Initialize RR pointers
* Mark all nodes idle

### What happens AFTER

You now have:

* Empty FIFOs
* Cycle = 0
* Interconnect ready to accept traffic

This explains why `SimpleInterconnect::cycle()` dominates perf early — it runs **every simulator cycle**.

## 4️⃣ `cycle()` — the HEART of the interconnect

This is what perf is screaming about (`~67%`).

### What happens BEFORE

State at cycle **C**:

* `_in_buffers` contain queued packets
* Some packets may have `finish_cycle <= C`
* `_out_buffers` may contain packets waiting to be popped

---

### What happens INSIDE (step by step)

```cpp
for each dest:
```

Each destination independently arbitrates.

```cpp
src_start = _rr_next_src[dest];
```

Round-robin fairness pointer.

```cpp
for each src (RR order):
```

Check **all possible sources**.

```cpp
if in_buffers[src][dest] not empty
AND front.finish_cycle <= _cycles
```

This is the **latency check**.

If true:

* Packet is *ready to arrive*

```cpp
_out_buffers[dest].push(packet)
_in_buffers[src][dest].pop()
_rr_next_src[dest] = src + 1
break;
```

Important:

* **At most ONE packet per destination per cycle**
* Arbitration cost = O(N)

Finally:

```cpp
_cycles++;
```

---

### What happens AFTER

State at cycle **C+1**:

* Some packets moved from in → out buffers
* RR pointers advanced
* Cycle counter incremented

This is exactly why perf shows:

```
SimpleInterconnect::cycle() → is_empty → push → pop
```

---

## 5️⃣ `push(src, dest, request)`

This models **injection into the network**.

### BEFORE

* Request is generated by core or DRAM

### INSIDE

```cpp
if buffer empty:
  finish = now + latency
else:
  finish = last.finish + 1
```

This means:

* First packet pays full latency
* Later packets serialize (1 per cycle)

Then packet is queued:

```cpp
_in_buffers[src][dest].push(entity)
```

### AFTER

* Packet is *in flight*
* It cannot be delivered before `finish_cycle`

This is how **contention is modeled**.

---

## 6️⃣ `is_empty(nid)`

Simple check:

```cpp
return _out_buffers[nid].empty();
```

Meaning:

> “Does destination node have anything ready to receive?”

Frequently used by:

* Core
* DRAM
* Scheduler

Perf showing this often → **backpressure**.

---

## 7️⃣ `top(nid)` / `pop(nid)`

Classic queue interface.

```cpp
top() → peek packet
pop() → consume packet
```

These are called **after `cycle()`** has moved packets into `_out_buffers`.

---

## 8️⃣ `running()` and `is_full()`

Currently stubs:

```cpp
bool running() { return false; }
bool is_full(...) { return false; }
```

So:

* Interconnect never stalls injection
* Infinite buffer capacity

This explains:

> why SimpleInterconnect dominates runtime
> why cores are rarely blocked by ICNT fullness

## 9️⃣ Why perf shows `SimpleInterconnect::cycle()` so high

From the code:

* Called **every simulator cycle**
* Double loop: `O(N²)`
* Always runs, even if no traffic
* No early exit

So perf result:

```
~67% SimpleInterconnect::cycle()
```

is **expected and correct**.

## 🔟 What is happening BEFORE and AFTER calls (summary)

### Typical simulator loop

```
Simulator::cycle()
 ├── Core::cycle()
 │    └── SimpleInterconnect::push()
 │
 ├── DramRamulator2::cycle()
 │
 ├── SimpleInterconnect::cycle()   <-- moves packets
 │
 ├── Core::pop_memory_response()
 │    └── SimpleInterconnect::pop()
```

This is the **real execution order**, not obvious from perf alone.

## 🧠 Key insights (important)

1. This is a **very simple ICNT**
2. Latency is enforced via `finish_cycle`
3. Contention is serialized per `(src,dest)`
4. Arbitration is O(N²)
5. Buffers are unbounded
6. Logging inside `cycle()` would be extremely expensive
